# <코드> Design — 진행 관리

## 시작하기 — 이 단계 세션 진입점
> ⚠️ 새 항목(단위 하나의 상세 설계)은 산출물 전에 플랜 모드로 플랜을 작성·검수·승인받는다.

읽는 순서: 1 이 README → 2 `progress.md` · `open-questions.md` · (있으면) 루트 `handoff.md` → 3 `checklist.md` → 4 관련 설계(`map.md` · 단위 설계 · `plan/overview.md` · `dev/global/`)

현재 브랜치가 `dev/README.md` 표의 진행 중 사이클 브랜치(`cycle/<코드>`)인지, 사이클 README의 "현재 단계"가 Design인지 먼저 확인한다.

## 목적
이 사이클 구현의 기준이 되는 **바뀔 설계(to-be)** 를 단위별로 만든다. 단위 하나(= 항목 하나)당 플랜 모드를 새로 켜고, 그 단위의 상세 설계를 `<개념>-design.md`(번호 없는 개념명)로 쓴다.
설계 문서는 **개념 하나당 하나**다 — 서로 맞물린 단위 여러 개는 한 문서에 함께 담고, `map.md`의 "참조" 칸이 모두 그 문서를 가리킨다.
기존 시스템을 바꾸는 단위라면 `dev/global/`의 해당 개념 문서를 출발점으로 삼고, 바뀔 모습을 이 폴더의 문서에 쓴다(global은 승격 때 또는 사이클 밖 작업에서 바뀐다).

## 진행 방식
항목 순서의 원문은 여기 한 곳에만 둔다. 한 항목(단위 설계) = 아래 1~9.

1. **맥락 잡기** — 이 README → progress · open-questions · handoff.md → checklist에서 단위 하나 선택(의존 순서 — 앞 결정이 뒤의 전제를 바꾸는 것부터).
2. **플랜 모드** — 조사 + 필요한 **실측**(`../evidence/`) → 플랜에 설계 내용(초안)을 담아 → 플랜 검수(GO까지) → 사용자 승인.
   플랜 파일 **마지막 줄**에 검수 기록 줄(`플랜 검수: GO — <검수자·회차> — 본문 <해시8>`). 사용자가 정할 것은 텍스트로 한 번에 한두 개씩, 근거·장단점·권장과 함께 묻는다. 추론은 반영 전에 확인받는다.
3. **명세 고정** — 플랜 모드에서는 파일을 쓰지 않으므로, 승인 뒤 설계 문서 `<개념>-design.md`로 옮겨 쓴다. 외부 리뷰 보강이 있으면 `checklist.md`에 반영 상태를 적는다.
4. **작업** — 설계 문서 작성. 설계(단위 구성·의존·분기·사람 개입 지점)는 사용자와 의논해 확정한 뒤에만 바꾼다. 편의는 근거가 아니다.
5. **검수** — 설계 문서를 독립 검수자에게(`CLAUDE.md` "플랜 검수" 절의 검수자·모델). P0·P1이 없을 때까지 반복, 재검수는 직전 지적 해소 + 회귀만. 지적은 문서·코드로 확인해 반영하고, 반영하지 않으면 이유를 기록한다.
6. **역전파 + 미결 정리** — `../plan/checklist.md`의 역전파 체크리스트를 수행(`map.md`·`plan/overview.md`·open-questions). 이 단계 ID로 인용할 수 있는 미결은 이 단계 open-questions에, 아니면 `project-memory/open-questions.md`.
7. **로그** — checklist 항목을 `[x]`로 하고 한 단락 요약 + 설계 문서 링크. progress 맨 위에 로그, "다음 착수 지점" 갱신. 비자명한 결정·함정은 `project-memory/`에.
8. **커밋·푸시** — GO 뒤에만, 사이클 브랜치에 설계 문서 · 역전파한 문서 · checklist 요약 · progress · `project-memory/` 기록을 **한 커밋**으로. GO 전 중간 상태는 `handoff.md`.
9. **핸드오프 점검** — 맥락 없는 서브에이전트에게 "이 README를 읽고 다음 항목 진행해줘"를 주고 실행 없이 계획만 보고받는다. 전부 만족해야 통과:
   ① 다음 항목을 `progress.md`의 "다음 착수 지점"과 같게 짚는다 ② 플랜 모드부터 들어간다고 답한다 ③ 먼저 읽을 문서·명세를 찾아낸다
   ④ 이미 끝난 항목·지운 ID·옛 명령을 현재 할 일로 읽지 않는다 ⑤ 작업 트리가 깨끗하다(항상 필수) — 원격이 있고 push가 허락된 프로젝트면 원격과 같아야 하고, 원격이 없으면 확인 대상이 아니며, 사용자가 push를 보류했다면 그 사실(이유·push 시점)이 `progress.md`나 `handoff.md`에 있으면 통과
   ⑥ 현재 브랜치가 진행 중 사이클 브랜치와 같고 사이클 README의 "현재 단계"가 점검한 단계와 같다.
   어긋나면 원인 문서를 고쳐 커밋·푸시하고 같은 점검을 다시 한다. 통과하면 progress에 한 줄 남기고 추가 커밋·푸시.

## 단계 전환 (Design → Impl)
게이트 — **설계 완료 범위**(기본 A: 이 사이클의 모든 단위 / 선택지 B: 첫 슬라이스에 속한 단위 — B는 검증되지 않은 방식이며 채택은 사용자가 정한다)의
`checklist.md` 항목 `[x]` · 그 범위의 외부 리뷰 보강 반영 · 그 범위의 `open-questions.md` 해소 또는 preflight 이관 · 역전파 grep 잔존 0, 그리고 **"구현 준비 상태 점검" 세션** 완료:
① 가정 실측 ② 문서 간 어긋남(취소선 누락·옛 서술 혼재) 0 ③ `impl/README.md`의 확정 전제 작성 ④ `impl/checklist.md`가 `map.md`의 "구현 구분" 열을 Phase로 편성.
남은 미결은 `impl/open-questions.md`로 이관하고 여기에는 `[이관 YYYY-MM-DD → impl/open-questions.md <ID>]`를 남긴다. 사이클 README의 "현재 단계"를 갱신한다.
